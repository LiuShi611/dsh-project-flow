# 项目流程（Project flow）

把一个大任务拆成五段接力：先问清楚、再规划、再实施、再自检、最后按你最初的要求验收汇报。中间三段各开独立子会话，只传任务书，不传过程。

作者：刘适 ｜ 版权 © 2026 刘适 ｜ 许可：PolyForm Small Business License 1.0.0（见包根目录 `LICENSE`）

小公司（100 人以下且上一财年收入低于 100 万美元）和个人直接用，商业用途也含在内；超过这个规模见 [COMMERCIAL.md](COMMERCIAL.md)。本软件按「现状」提供，使用后果由使用者自负。

## 为什么这样拆

一条对话处理大任务，越往后上下文越重，要么撑爆、要么上游报错、要么质量下滑。这里把重的部分移出去：

- 规划、实施、自检各是一个独立子会话，跑完即弃，它们的读取、试错、编译输出都不会回到你的对话里。
- 三段之间只传「任务书」——规划写给实施一份，自检打回时再写一份修正任务书。不搬完整对话。
- 主对话只留两次东西：开头问你要什么，结尾给你一份验收汇报。

所以对话不会因为任务大而变长，中间过程不进上下文，token 主要花在干活本身，而不是花在重复搬运背景。

## 五个环节

| 段 | 在哪跑 | 做什么 |
|---|---|---|
| 1 问意图 | 主对话 | 一次只问一个问题，问出真实意图，和你确认一份逐条可核对的「要求清单」 |
| 2 规划 | 子会话 | 拿到意图和要求，产出一份给实施用的施工任务书 |
| 3 实施 | 子会话 | 只按任务书干活，不自己扩大范围 |
| 4 自检 | 子会话 | 默认怀疑，逐条核对；不合格必须产出一份完整的修正任务书打回第 3 段 |
| 5 验收 | 主对话 | 对照你最初的要求逐条核：哪些做到、哪些没做到、额外做了什么、返工几次 |

同一时刻只有一段在动，其余都在休息。所以「现在在第几段」本身就是真实进度。

## 打回与停机

- 自检不合格时，必须给出可执行的修正任务书，不能只写「不合格」。
- 最多返工 2 次（可配）。第二次仍不通过就停机，把「卡在哪」交给你定夺。
- 自检判不合格却没给出修正任务书时，同样停机，不盲目重跑。
- 任何一段异常结束（报错、超时、被取消）都直接停机，不带着残缺往下走。

停机的理由：如果任务书写清楚了还不通过，问题多半在规划或判定，不在实施。继续循环只是重复烧钱。

## 自愈（0.2.0 起）

报错、崩溃、插件重载、窗口被杀之后，不该从头再来一遍。这里分三种情况各自处理：

### 1. 某一段异常结束 → 自动重试

单段失败（上游断连、子会话报错、模型路由临时不可用）会按 `maxStageRetries` 重试，间隔按 `stageRetryDelayMs` 递增（第一次等 1 倍，第二次等 2 倍）。重试次数与每次尝试都写进 `run.log`。

三次都失败才判 `blocked`，并在返回结果里写清是真错在哪一段、试了几次。用于重试的判断只看「这一段有没有正常结束」，不看内容质量——内容质量是自检段的事。

### 2. 某一段卡住不结束 → 超时切断

每段有自己的截止时间 `stageTimeoutMs`（默认 15 分钟）。超时即取消该子会话，按失败处理（同样走重试），不会让整条流水挂死在那里。

用户主动中断（Esc、取消会话）**不会**重试——那是你叫停的，不是故障。

### 3. 进程崩了、插件重载、窗口被杀 → 续跑

`state.json` 与产物都是磁盘上的普通文件，所以崩溃不会丢进度：

- 每次运行会写一个 `run.lock`（含 pid 与心跳，每分钟刷新）。进程没了，锁就成了「遗留锁」。
- 下一次对同一项目动手，`acquireLock` 发现持有者进程已死、且心跳超过 `staleLockMs`（默认 30 分钟）没动，就直接把旧锁挪开接手续跑。
- 中断留下的 `state.json` 会带 `interruptedAt` 与 `lastError`，`project_status` 会把这两项显示出来。
- `project_resume` 读 `02-plan.md`、最新的 `03-build-*.md`、`03-correction-*.md`，重建施工任务书与实施自述，从**中断的那一段**接着跑：规划已过就不重跑规划，实施自述已有就不重做实施。

崩溃时 `state.json` 本身也可能写坏。`project_doctor` 会检测并处理：

| 症状 | doctor 的处理 |
|---|---|
| `state.json` 解析失败 | 先改名成 `state.json.corrupt-<时间戳>` 留证，再按 `01`–`05` 产物推断段位重建，并从 `01-intent.md` 里把意图与要求清单抠回来（这两项续跑必需，别的地方补不出来） |
| 有锁但持有者进程已死且心跳过期 | 把锁改名成 `run.lock.stale-<时间戳>` |
| 状态停在 `planning` / `building` / `checking` 这类没收尾的值 | 补 `interruptedAt`，状态改成「…（中断）」，提示可以 `project_resume` |

`project_doctor` **默认只报告，不动任何文件**；`fix: true`（命令 `/flow-doctor fix`）才真的修。自动修复放在显式调用里，是因为默默改状态比留下一个能看的坏状态更糟。

### 自愈的边界（说清楚，免得你以为万能）

- 只能救「进度」和「工作区」，救不了「做错的活」。一段跑完但做得不对，那是自检段的事，自愈不参与判断对错。
- 续跑依赖产物完整。`02-plan.md` 里的施工任务书要是没了，实施段接不上，会明确告诉你接不上，而不是瞎编一份任务书往下跑。
- 重试对「模型持续不可用」「上游额度耗尽」这类稳定故障无效，重试只是在烧时间；三次后照样停机。
- 进程内状态（`running` 表）随进程消失，跨进程的互斥只能靠 `run.lock`，所以要靠 pid + 心跳判活，不能只看文件在不在。

## 回滚

自愈只管「没跑完」，管不了「跑完了但做错了」。跑完却发现改废了，靠回滚。

### 快照怎么来的

每个项目自己带一个裸 git 仓库：

```
.project-flow/<项目名>/snap.git      ← 对象库，不在你的仓库里
  --work-tree=<工作目录>              ← 你的真实工作区
```

**不在工作区里 `git init`**：不给你塞 `.git`，不产生你没要求的提交。哪怕工作区本来就不是 git 仓库也能用。

`snap.git/info/exclude` 里排掉了 `.project-flow/`、`.git/`、`node_modules/`、`.venv/`、`dist/`、`build/` 等，否则每打一次快照都在给自己拍照，第一次试就撞上了这个坑。

打快照的时机：

| 时机 | 标签 | 用途 |
|---|---|---|
| 每次实施**前** | `实施前 R1`、`实施前 R2`… | 这才是回滚目标：「回到这一轮动手之前」 |
| 每次实施**后** | `实施后 R1`、`实施后 R2`… | 对照「这一轮到底改了什么」 |
| 真回滚**前** | `pre-rollback <目标>` | 逃生口：回错了还能再回去 |

工作区没有变化时复用上一张快照，不会堆一串空提交。

### 两种回滚粒度

`project_rollback` 的 `mode`：

**`full` 整棵恢复（默认）**——把整个工作区退到目标快照的样子：改过的还原，快照里没有的文件删掉。干净彻底。代价是会连你在这期间手改的东西一起撤掉。

**`precise` 只还原那次动过的文件**——只处理那一轮实施报告过（或快照 diff 里看出来的）文件，你手改的其他文件一个不碰。代价是：实施段漏报的文件它不知道，也就不会清。测试里专门验过这个取舍——`junk.txt` 是实施段私建、没写进自述的，precise 模式留着它，`full` 模式才清掉。

### 必须先干跑

`dryRun` 默认 `true`：只列出「哪个文件会怎样」（新增/修改/删除），一个字节都不动。看过没问题再 `dryRun: false`。

不传 `to` 就是「最近一轮实施之前」；写 `2` 是「第 2 轮实施之前」；写 commit 也行。

### 完整例子

```
project_snapshots { project: "my-app" }
→ 5 张快照（新→旧）：
  a2a8b800  2026-11-25T10:52:34  pre-rollback 14dc871e
  9f0ee8a7  2026-11-25T10:52:28  实施前 R2          ← 第 2 轮实施前
  ...

project_rollback { project: "my-app", to: "1" }
→ 干跑：将要改动 2 个文件
    修改  src/a.txt
    新增  src/junk.txt

project_rollback { project: "my-app", to: "1", mode: "full", dryRun: false }
→ 已回滚，工作区和目标快照一致。
   删掉了 1 个快照里不存在的文件。
   回滚前的现场已存为快照 4478994b，回错了还能再回去。
```

### 回滚的边界

- **需要 git。** 没有 git 时流水照常跑，只是每次会在 note 里写「快照不可用」，`project_rollback` 会明确告诉你做不了。
- **大目录会慢。** 每张快照是一次 `git add -A`。几万个小文件或几个 G 的权重文件会明显拖慢；用 `snapshotExcludes` 把它们排掉。
- **被 exclude 的东西不在快照里。** 排掉的目录回滚不会动，这是故意的：那些本来就是可以重装的产物。
- **precise 依赖自述诚实。** 实施段漏报的文件它不清。要彻底干净就用 `full`。
- **回滚不改流程状态。** `state.json` 里的段位、返工次数不会因为回滚而倒退。要重跑就在回滚后跑 `project_resume` 或重新 `project_run`。

## 用法

### 斜杠命令

在输入框敲 `/` 就能看到七个命令，选中即用：

| 命令 | 作用 |
|---|---|
| `/flow 你的任务` | 开工作模式，把当前任务按五段跑。不带任务描述时会先问你 |
| `/flow-status` | 看当前项目跑到第几段、返工几次、上次中断在哪 |
| `/flow-models` | 看五段各用什么模型、自愈与快照参数 |
| `/flow-resume 项目名` | 接续被中断的项目（不带项目名先列出全部） |
| `/flow-doctor [fix]` | 体检工作区；加 `fix` 才动手修 |
| `/flow-snapshots 项目名` | 看这个项目有哪些快照可以回滚 |
| `/flow-set 阶段 模型名` | 改某段用的模型，改完立即生效，不用重启 |

`/flow` 只是把「开工作模式」这个意图告诉模型，真正的五段执行还是由模型调 `project_run` 完成。这样做的好处是不依赖界面面板，插件不会因为 UI 崩溃而用不了。

### 改模型：不用改配置文件，不用重启

```
/flow-set 规划 deepseek-v4.1-flash
/flow-set 实施 hy4flash
/flow-set 自检 deepseek-v4.1-flash
/flow-set 重试 3
/flow-set 清空
```

改动写到 `%DSH_HOME%\project-flow.<profile>.json`（桌面版即 `C:\Users\<你>\.dsh\project-flow.desktop.json`），下一次跑任务时直接生效。原理是每次执行前重新读覆盖文件，而不是只在插件加载时读一次。

覆盖文件是**分层合并**的：`project-flow.<profile>.json` 优先，`project-flow.json` 作为垫底也参与合并。所以早先写在共享文件里的单项设置不会因为 profile 文件出现就整个失效。

`/flow-set 清空` 会把该段恢复成「继承当前模型」。

### 五段各自的模型分工

| 段 | 模型 | 为什么 |
|---|---|---|
| 1 问意图 | kimi-k3.1-pro | 要问出你真正的想法，用聪明的 |
| 2 规划 | deepseek-v4.1-flash | 出任务书，中等模型够用 |
| 3 实施 | hy4flash | 动手干活，便宜且量大 |
| 4 自检 | deepseek-v4.1-flash | 消耗最大的一段，用便宜的 |
| 5 验收 | 主对话模型 | 对照你的要求逐条核 |

**kimi 只负责问想法和最终验收，不要拿它跑自检**——自检要读大量文件、逐条比对，是所有阶段里最耗 token 的一段，用 kimi 不划算。

第 1 段和第 5 段跑在主对话里，模型只能用界面顶部切，`/flow-set` 改不了这两段。

### 不开命令也能用

接到任务时助手会先问一句「这次开工作模式吗」。你说开，它就先问清意图，确认要求清单，然后调 `project_run` 跑流程，最后在主对话里给你验收汇报。

### 八个工具

- `project_run` — 跑一个项目的第 2 至 4 段，返回一份压缩后的结果
- `project_resume` — 接续被中断的项目，从中断那段接着跑
- `project_doctor` — 体检遗留锁、损坏状态、悬空阶段；默认只报告
- `project_snapshots` — 列出全部快照与每次实施动了哪些文件
- `project_rollback` — 回滚到某个快照，`full` 或 `precise`，默认干跑
- `project_status` — 看某个项目现在在哪一段；不带项目名就列出全部
- `project_models` — 看五段现在各用什么模型、自愈与快照参数
- `project_set_model` — 改某段模型（`/flow-set` 的工具形态）

### 产物在哪

工作目录下的 `.project-flow/<项目名>/`：

```
01-intent.md          确定的意图与要求
02-plan.md            方案与施工任务书
03-build-1.md         第 1 次实施自述
04-check-1.md         第 1 次自检结论
03-correction-1.md    修正任务书（有返工时才有）
03-build-2.md         第 2 次实施自述
...
05-report.md          交接给验收
state.json            当前段位、状态、返工次数、中断信息、最后的错误、每次实施的快照与改动文件
run.log               每次尝试、快照与自愈动作（超过 512 KB 自动轮转成 run.log.1）
run.lock              运行中的锁；正常结束后自动删除
snap.git/             项目自己的快照仓库（裸仓库，不含工作区副本）
```

## 配置

在 `cordis.patch.yml` 里改：

| 键 | 默认 | 作用 |
|---|---|---|
| `provider` | `spawn` | 默认子会话后端 |
| `intentModel` | 空 | 第 1 段期望的模型；只用于提示你切换，插件改不了实际模型 |
| `planProvider` / `planModel` | 空 / 空 | 第 2 段（规划）的 provider 和模型 |
| `buildProvider` / `buildModel` | 空 / 空 | 第 3 段（实施）的 provider 和模型 |
| `checkProvider` / `checkModel` | 空 / 空 | 第 4 段（自检）的 provider 和模型 |
| `maxRework` | `2` | 最多返工几次 |
| `maxConcurrentProjects` | `2` | 同时能跑几个项目 |
| `maxStageRetries` | `2` | 单段异常后额外重试几次（总尝试 = 1 + 这个值） |
| `stageRetryDelayMs` | `3000` | 重试基础间隔，第 n 次等 n 倍 |
| `stageTimeoutMs` | `900000` | 单段截止时间（毫秒），0 表示不限 |
| `staleLockMs` | `1800000` | 锁心跳超过这个时长没更新，就当作崩溃遗留（毫秒） |
| `snapshotEnabled` | `true` | 是否在每次实施前后打快照；关掉就没有回滚 |
| `snapshotExcludes` | 空 | 额外的排除规则，逗号或换行分隔，叠加在内置清单上 |

空值表示继承当前模型；`*Provider` 留空则用上面的 `provider`。

第 2、3、4 段可以各用不同模型。第 1 段（问意图）和第 5 段（验收）跑在主对话里，模型由界面顶部的选择器决定，插件没有切换它的权限——`intentModel` 只是一个期望值，用来提醒你手动切。

如果给某段指定的模型在你的 profile 里没有被授权，插件不会崩，会退回当前模型继续跑，并在返回的结论里写明哪一段回退了、为什么。要确认实际生效的模型，用 `project_models` 查。

### 当前配置

```yaml
planModel: deepseek-v4.1-flash    # 规划
buildModel: hy4flash              # 实施
checkModel: deepseek-v4.1-flash   # 自检
intentModel: kimi-k3.1-pro        # 期望值，需手动在主对话切换
maxStageRetries: 2                # 单段失败重试 2 次
stageTimeoutMs: 900000            # 单段 15 分钟截止
staleLockMs: 1800000              # 锁 30 分钟无心跳算遗留
snapshotEnabled: true             # 每次实施前后打快照
```

## 边界

- 一次 `project_run` 跑完一整条流水，中途不能插话。要中途叫停就用会话中断；叫停后可以 `project_resume` 接着跑。
- 第 1 段和第 5 段必须在主对话，因为子会话问不了你，也汇报不了给你。
- 产物是纯文件，不依赖数据库；迁移项目目录即可搬走全部记录（含快照历史）。
- 同一项目同时只能有一个实例在跑，按项目名加锁；跨进程用 `run.lock` + pid + 心跳判活。
- 三段模型只影响子会话；主对话的模型永远是界面顶部那个。
- 自愈只处理「没跑完」，回滚只处理「跑完了但改废了」——两件事，别混。
