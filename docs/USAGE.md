# 项目使用说明

dsh-project-flow ｜ 作者：刘适

这份说明讲三件事：它解决什么问题，每段在做什么，出问题的时候怎么办。想直接上手，看第二节和第三节就够了。

---

## 一、它解决什么问题

用一条对话跑一个稍大的任务，会撞上三个麻烦：

上下文越跑越重，前后互相污染。跑到后半段，模型开始忘记前面确认过什么，你说过不要动的地方它动了，说好的标准它松了。

中途出错就得从头再来。上游断连、子会话报错、进程被杀，之前跑的进度全废，重新跑一遍还要重新烧一遍 token。

跑完了才发现做错了。自检说通过，你看了一眼，不对。这时候没有退路，只能手动一个个改回去。

这个插件对着这三件事各出一样东西：

**中间三段挪出主对话。** 规划、实施、自检各开一个独立子会话，跑完即弃。它们读的文件、试错的输出都不回到你的对话里。三段之间只传任务书。主对话只多出一条结果，不是整条流水。

**进度全部落在磁盘上。** 段位、返工次数、每次实施动了哪些文件、快照提交号，都写在 `.project-flow/<项目名>/` 里，纯文件，不进数据库。所以跑崩了能从中断那段接着跑，不用从头来。

**每次实施前后自动打快照。** 跑完发现改废了，退回去。回错了还能再退回来。

## 二、五段在做什么

第 1 段和第 5 段跑在主对话里，因为子会话问不了你，也汇报不了给你。中间三段跑在独立子会话里。

**第 1 段 问意图**（主对话）

一次只问一个问题，问出真实意图，和你确认一份逐条可核对的要求清单。这份清单后面每一段都拿在手上，自检照着它逐条验，验收照着它逐条核。

**第 2 段 规划**（子会话）

拿到意图和要求，产出一份给实施用的施工任务书：要做什么、动哪些文件、按什么顺序、每步的验收标准、边界与禁止事项。

**第 3 段 实施**（子会话）

只按任务书干活。它看不到用户，也看不到规划者的思考过程，任务书就是全部依据，不自己扩大范围。干完输出一份自述：做了什么、改了哪些文件、哪里和任务书不一致、哪里没做完。

**第 4 段 自检**（子会话）

职责是挑毛病，不是确认通过。默认怀疑，逐条对照任务书，必要时读文件核对，不只信实施环节的自述。不合格必须产出一份能直接照着干的修正任务书，打回第 3 段。

只写「不合格」「请修改」这种没有内容的话，按规则停机，不盲目返工——因为如果任务书写清楚了还不通过，问题多半在规划或判定，不在实施，继续循环只是重复烧钱。

**第 5 段 验收**（主对话）

拿结果对照你最初的要求逐条核：哪几条做到了、哪几条没做到、额外做了什么、返工几次、代价和残留风险。

## 三、怎么用

### 开一个任务

在输入框敲 `/flow`，后面跟任务描述：

```
/flow 给这个 Python 项目补一套 pytest 测试，覆盖登录和支付两个模块
```

不带描述也行，它会先问你。

接上之后它会先问意图，确认要求清单，然后跑完整条流水，最后在主对话给你验收汇报。中间过程不进对话，你只看到开头和结尾。

### 看进度

```
/flow-status
```

输出一行，形如：

```
my-task：第 3 段「实施」 · building，已返工 1 次
```

同一时刻只有一段在动，所以这段文字就是真实进度。

### 出了错怎么办

**跑崩了、窗口被杀、插件重载了**——先看状态：

```
/flow-status
```

如果显示「上次中断于 …，跑 project_resume 续上」，就用：

```
/flow-resume my-task
```

它会按磁盘上的产物重建上下文，从中断那段接着跑。已经通过的段不重做。

**怀疑工作区有问题**（遗留锁、状态文件损坏、有阶段开了头没收尾）：

```
/flow-doctor
```

只报告，不动任何文件。确认要修再加 `fix`：

```
/flow-doctor fix
```

会移开死锁、按产物重建状态、把没收尾的段标成中断。

### 跑完了发现做错了

先看有哪些快照可以退：

```
/flow-snapshots my-task
```

输出像这样，标了每一张对应哪一轮实施：

```
项目 my-task：5 张快照（新→旧），回滚时用 commit 或「第 N 轮」都行。
a2a8b800  2026-11-25T10:52:34+08:00  pre-rollback 14dc871e
9f0ee8a7  2026-11-25T10:52:28+08:00  实施前 R2　← 第 2 轮实施前
4478994b  2026-11-25T10:52:30+08:00  实施后 R2　← 第 2 轮实施后
...
```

然后回滚。**默认是干跑**，只告诉你会动哪些文件，一个字节都不改：

```
project_rollback { project: "my-task", to: "1" }
```

看清楚再真回滚：

```
project_rollback { project: "my-task", to: "1", mode: "full", dryRun: false }
```

两种粒度：

`full` 整棵恢复到目标快照。改过的还原，快照里没有的新增文件删掉。干净彻底，但会连你在这期间手改的东西一起撤掉。

`precise` 只还原那一轮实施动过的文件。你手改的其他文件一个不碰。代价是实施段漏报的文件它不知道，也就不会清。

说不清就先用 `full`。

真回滚之前它会自动再打一张 `pre-rollback` 快照，并告诉你提交号。回错了拿这个号再滚回去。

### 换模型

```
/flow-models
```

看五段各用什么模型，以及自愈和快照的参数。

```
/flow-set 实施 hy4flash
/flow-set 规划 deepseek-v4.1-flash
/flow-set 自检 清空
```

`清空` 表示恢复成继承当前模型。改完立即生效，不用重启。

第 1 段和第 5 段跑在主对话，模型只能用界面顶部的选择器切，`/flow-set` 改不了这两段。

## 四、我建议的模型分工

| 段 | 模型 | 理由 |
|---|---|---|
| 1 问意图 | 用聪明的 | 要问出你真正的想法，这一段省不得 |
| 2 规划 | 中等模型够用 | 出任务书，不需要最强的 |
| 3 实施 | 便宜且量大 | 动手干活，消耗大 |
| 4 自检 | 便宜的 | 要读大量文件、逐条比对，是所有阶段里最耗 token 的一段 |
| 5 验收 | 主对话模型 | 对照你的要求逐条核 |

别拿最贵的模型去跑自检。自检的 token 消耗是四段里最高的，用贵模型不划算，而且它做的是核对，不是创造。

## 五、要知道的限制

**自愈只管「没跑完」，管不了「跑完了但做错了」。** 后者是回滚和自检的事。别指望重试能救一个逻辑就错的方案。

**回滚需要 git。** 没有 git 时流水照常跑，只是每次在结论里写「快照不可用」，回滚会明确告诉你做不了。

**快照不覆盖被排除的目录。** `node_modules/`、`.venv/`、`dist/`、`build/` 这些默认不进快照，回滚不会动它们。这是故意的——那些本来就是能重装的东西。大目录要额外用 `snapshotExcludes` 排掉，否则每张快照都在拖慢。

**回滚不改流程状态。** 段位和返工次数不会因为回滚而倒退。要重跑就在回滚后跑 `/flow-resume` 或重新开一个。

**一次 `project_run` 跑完一整条流水，中途不能插话。** 要叫停就用会话中断；叫停后可以 `/flow-resume` 接着跑。

**第 1 段和第 5 段必须在主对话。** 子会话问不了你，也汇报不了给你。

## 六、产物在哪

工作目录下的 `.project-flow/<项目名>/`：

```
01-intent.md          确定的意图与要求
02-plan.md            方案与施工任务书
03-build-N.md         第 N 次实施自述
04-check-N.md         第 N 次自检结论
03-correction-N.md    修正任务书（有返工时才有）
05-report.md          交接给验收
state.json            段位、状态、返工次数、中断信息、每次实施的快照与改动文件
run.log               每次尝试、快照与自愈动作
run.lock              运行中的锁，正常结束后自动删除
snap.git/             项目自己的快照仓库
```

这些都是普通文件。迁移项目目录就能搬走全部记录，含快照历史。

`run.log` 是排查问题时第一个该看的东西：每次尝试、每次快照、每个自愈动作都在里面，超过 512 KB 自动轮转成 `run.log.1`。
